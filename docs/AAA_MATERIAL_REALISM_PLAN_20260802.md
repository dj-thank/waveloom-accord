# マテリアルとリアリズム — 診断と実装計画（2026-08-02）

## 0. 結論を先に

**ジオメトリの問題は概ね解けた。リアルに見えない原因はマテリアルにある。**

このセッションで街区を23→75棟、丸柱929本、アーチ102、敷石目地1,541本まで進めたが、
それでも「まだ全然リアルじゃない」という評価は**正しい**。理由は単純で、決定的である。

```js
// client/render.js:1196  _presentationMaterial()
return new THREE.MeshStandardMaterial({
  color, roughness, metalness, emissive, emissiveIntensity,
});
```

**マップの描画インスタンス 21,214個すべてが、テクスチャを1枚も持っていない。**
`map` も `normalMap` も `roughnessMap` も `aoMap` も無い。1マテリアル＝1つの平坦な色で、
面の中に情報が存在しない。ジオメトリをどれだけ足しても、**面that自体が無地の塗り面**
である限り、CGとしてのリアリティは出ない。

参照マップは 527マテリアルに対し **1,443枚の画像**（＝1マテリアルあたり2.7枚：
albedo + normal + roughness/AO）を持つ。うちは 27マテリアルに対し **0枚**である。
これが 387 vs 18 三角形よりも大きい、本当の差である。

| | 参照 | 大潮井 | 比 |
|---|---:|---:|---:|
| マテリアル数 | 527 | 27 | 1/20 |
| テクスチャ画像 | 1,443 | **0** | — |
| 1マテリアルあたりのマップ | 2.7 | **0** | — |
| 面内の情報量 | 高（albedo/法線/粗さが画素ごとに変化） | **ゼロ（単色）** | — |

補足: 当たり判定サーフェス（床・壁の `mats[tag]`）だけは `makeSurfaceTexture()` で
64×64の手続きノイズを持つ。しかしこれは **albedoの明度ゆらぎのみ**で、法線もAOも
粗さ変化も無く、しかも presentation の21,214個には**適用されていない**。

## 1. なぜ「単色の面」はリアルに見えないのか

リアルさは輪郭ではなく**面の光の返し方**で決まる。実物の面は次の4つを同時に持つ。

1. **アルベド変化** — 同じ壁でも場所ごとに色が違う（汚れ、色むら、経年、素材の粒）。
2. **法線変化** — 微細な凹凸が光を散らす。石は粗く、金属は方向性を持つ。
3. **粗さ変化** — 濡れた所は光り、乾いた所はマットになる。均一な粗さは樹脂に見える。
4. **遮蔽（AO）** — 隅・継ぎ目・接地部が暗く落ちる。これが「物が置かれている」感覚を作る。

現状は4つとも**ゼロ**である。だから：
- どの面も同じ明るさで、距離感と質量感が出ない
- 稜線でしか形が読めない（＝「色付きグレーボックス」の正体）
- 接地部が浮いて見える
- 材質の違いが「色の違い」でしか表現されず、石も木も布も同じ質感に見える

**ジオメトリを足しても解決しない。** 面の中に情報を入れるまで、リアルにはならない。

## 2. この engine で取り得る手段

前提条件（変えられない制約）:
- Three.js + `InstancedMesh`（1層＝1ドローコール）で 113層 / 21,214インスタンス
- 実画面ドローコール上限 250（現在の最悪視点208）、三角形上限1,200,000（現在622K）
- 外部テクスチャアセットは存在しない（`assets-src/imagegen` に画像はあるが未接続）
- 決定論的ビルドが必須（`Math.random()` 禁止）

### 案A: 手続き生成 DataTexture（推奨・第一段階）

`makeSurfaceTexture()` を拡張し、**マテリアルごとに albedo / normal / roughness の
3枚組**を生成して `_presentationMaterial()` に渡す。

- 長所: アセット不要、決定論的、実装が閉じている、既存コードの拡張で済む
- 短所: 写真的なディテールは出ない（ただし「無地」からの改善幅が圧倒的に大きい）
- コスト: 27マテリアル × 3枚 × 128px² ≈ 4MB（GPU上）。**極めて安い**
- ドローコール増: **0**（既存マテリアルにマップを足すだけ）

生成すべきもの:

| マップ | 作り方 | 効果 |
|---|---|---|
| `map`（albedo） | 多周波ノイズ（低周波の色むら＋高周波の粒）＋材質固有パターン | 面内の色変化 |
| `normalMap` | 高さ場を作り、隣接差分から法線を算出 | 微細凹凸の陰影 |
| `roughnessMap` | 高さ場の逆相関（凹部は汚れて粗く、凸部は擦れて滑らか） | 質感の分離 |

**重要:** albedoノイズだけでは足りない。`normalMap` が入って初めて「面が光を拾う」。
現状の `makeSurfaceTexture` が albedo だけなのが、床がまだ平板に見える理由でもある。

### 案B: シェーダ改変（三平面投影ノイズ）

`onBeforeCompile` で標準マテリアルに三平面ノイズを注入する。

- 長所: UV不要（`InstancedMesh` のスケール差でUVが伸びる問題を回避）、テクスチャメモリ0
- 短所: 実装が重い、Three.jsのバージョン更新で壊れやすい、デバッグが難しい
- 位置づけ: 案Aで UV伸びが問題になった箇所にだけ、後から部分適用する

### 案C: オーサリング済みアトラス

`assets-src/imagegen` の生成画像をアトラス化して使う。

- 長所: 最も写実的
- 短所: 権利・容量・UV設計・ロード時間。現状 677MB のリポジトリをさらに増やす
- 位置づけ: 案Aが効いた後、ヒーロー建築など**近くで見る面に限定して**検討

**推奨: 案A → 効果測定 → 必要箇所に案B → 最後に案Cを限定適用。**

## 3. per-instance の色ゆらぎ（最も安い勝ち・即実施可）

`InstancedMesh.setColorAt()` は既に2箇所（`facadePanels` / `routePaving`）で使われて
いるが、**113層の presentation では未使用**である。

同じマテリアルの何百個ものインスタンスが**完全に同一の色**なので、反復が目立ち、
「同じ部品を並べただけ」に見える。

対策: 各インスタンスに決定論的な微小な色ゆらぎ（明度 ±6〜10%、色相はほぼ固定）を
`setColorAt` で与える。

- コスト: 三角形0、ドローコール0、インスタンスバッファに色属性が増えるだけ
- 効果: 反復感が大きく減り、密度が「量」ではなく「多様性」として読める
- 注意: 明度のみ振る。色相を振ると拠点ごとの色識別（現在地の可読性）が壊れる

**これは案Aより先にやってよい。** 最も費用対効果が高い。

## 5. 実装順序（費用対効果順）

### Step 1: metalness の物理的修正（コスト最小・即効）

中間 metalness を 0 か高値へ寄せる。**テクスチャ不要、三角形0、ドローコール0。**

```
basalt      .16 → .04    (石は非金属)
wetRock     .12 → .04
roofBlue    .26 → .05    (瓦として扱う)
roofCopper  .34 → .70    (金属屋根として扱う)
windowGlow  .28 → .00    (発光面)
lanternGold .20 → .00
indigoGlow  .28 → .00
copper      .72 → 維持   (正しい)
```

検証: `map_visual_finish` / `map_quality_score` / 実画面。
**注意:** `map_site_cladding.test.js` などがマテリアル名を固定しているが、
metalness値を固定するテストは無いはずなので確認してから変更する。

### Step 2: per-instance 明度ゆらぎ（`setColorAt`）

113層に決定論的な ±8% の明度ゆらぎ。三角形0・ドローコール0。

検証: インスタンス数不変、実画面で反復感の減少を目視。

### Step 3: 手続き normal + roughness マップ（本命）

`makeSurfaceTexture` を3枚組生成に拡張し、`_presentationMaterial` に接続する。
まず **面積上位5マテリアル**（basalt / cedar / shellShade / stoneJoint / shell、
計12,671インスタンス＝全体の60%）だけに適用して効果を測る。

検証: ドローコール不変（250以内）、三角形不変、GPU メモリ増を計測、実画面比較。

### Step 4: AO（接地の説得力）

選択肢:
- **頂点AO**: 各インスタンスの下端頂点を暗くする（安い、`InstancedMesh` と相性が良い）
- **SSAO ポストプロセス**: 全体に効くが描画コストが高く、250ドローコール予算とは別枠のGPU負荷
- **フェイク接地影**: 各インスタンスの足元に暗い板を1枚（インスタンス増＝予算圧迫）

推奨は**頂点AO**。予算を消費せず、接地感という最大の欠落を埋められる。

### Step 5: 環境マップ（IBL）

現状 `scene.environment` が無く、金属が反射するものが無い。
1枚の小さな procedural env map（空の色勾配）を `PMREMGenerator` で作って
`scene.environment` に入れるだけで、金属と光沢面が一気に立体的になる。
**コスト極小・効果大。Step 1 とセットで実施する価値がある。**

## 6. ライティングと後処理の現状と欠落

現状（`client/render.js`）:
- `HemisphereLight(0xdff6ff, 0x7c684b, 1.55)` — 空と地面の色
- `DirectionalLight(0xffe5bf, 3.4)` + `castShadow` + PCFSoft
- `AmbientLight(0xbdd9df, 0.18)`
- `ACESFilmicToneMapping`, exposure 1.08, sRGB出力
- フォグ・空・太陽ディスク・ヘイズあり

**良い点:** ACES トーンマッピングと影が既に入っているのは大きい。基礎は正しい。

**欠落:**
1. **環境マップが無い** → 金属・光沢面が「反射するものを持たない」（§5 Step 5）
2. **AOが無い** → 隅と接地が落ちない
3. **ポストプロセスが無い** → ブルーム（灯りの滲み）、色調整、被写界深度が無い。
   特に**ブルームは灯り2,143個を持つこのマップで効果が大きい**
4. **アンビエントが青一色** → 実際は空・地面・近接面から色が回り込む（バウンス）。
   Hemisphere があるので部分的には表現されている

優先度: 環境マップ > AO > ブルーム。

## 8. 検証方法（各ステップ共通）

1. 変更前に対象マテリアルの inst 数と現在値を記録
2. `node --test --test-reporter=dot 'tests/*.test.js'`（875、負荷なしで）
3. `tools/audit_map_quality_score.mjs --preview ...`（100/100維持）
4. `tools/audit_perf_views.mjs`（10視点すべて ≤250 calls / ≤1.2M tris）
5. **同一カメラで変更前後を撮って並べる**（`capture_map_views.mjs`）
6. `tools/audit_palette.mjs --files a.png,b.png` で暖色/金の面積比が壊れていないか
7. 当たり判定に触らないので**バランスゲートは不要**（ただし全体スイートには含まれる）

**説明で合格としない。必ず画像で判定する**（`docs/AAA_MAP_HANDOFF.md` の規則）。

## 9. やってはいけないこと

- **テストを緩めて通す**。マテリアル名や層数を固定するテストは意図があって存在する。
- **色相を大きく振る**。拠点ごとの色識別（現在地の可読性）は競技上の情報である。
- **発光を強くしてごまかす**。emissive を上げると HDR が飽和し、ACES が白く潰れる。
- **遠景にテクスチャを入れる**。距離で潰れて無駄になる。近景に集中させる。
- **参照からテクスチャ画像を取り込む**。権利上不可。手続き生成かオリジナル制作のみ。
- **ドローコールを増やす方向の解決**。250予算は競技フレームレートの前提である。

## 10. 期待される到達点（正直な見積もり）

Step 1〜5 を完了した場合:

- **達成できる**: 面の質感差（石/木/金属/布が見分けられる）、接地感、金属の反射、
  反復感の減少、灯りの説得力。**「色付きグレーボックス」からは確実に脱する。**
- **達成できない**: 写真的なディテール（実物のひび、傷、汚れの物語）、
  法線マップの精緻さ、参照レベルの1マテリアル2.7枚の情報量。

参照との差は「手続き生成 vs オーサリング済みテクスチャ」の差として残る。
そこを埋めるには案C（オーサリングアトラス）か、テクスチャアーティストの工数が要る。
**ただし Step 1〜5 だけで、体感の改善幅は今回のジオメトリ作業より大きいと見込む。**

## 11. 現在値（この計画の起点）

- 描画インスタンス 21,214 / 113層 / 27マテリアル / **テクスチャ0枚**
- 三角形 622K/1,200K、最悪視点ドローコール 208/250
- 全体テスト 875/0、品質スコア 100/100、collision digest 不変
- 参照: 527マテリアル / 1,443画像 / 2.7マップ per マテリアル

現状判定は `close` であり `aaa` ではない。マテリアルは**未着手の最大領域**である。
